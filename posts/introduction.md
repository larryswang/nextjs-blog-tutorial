## Why I start this blog
There are many system design tutorials and videos online, however, based on my personal experience, system design interviews seldomly go as expected. There can be multiple reasons for this:
1. The interviewer may ask from a different perspective from those tutorials(focus area)
2. You may not have heard this problems before
3. You learned the concept, but then don't know how to apply the learned concept. (Things you know vs things you are sufficient in)

As a result, usually system design interviews start with something simple, and use the existing knowledge to resolve the problem. For example, if you got asked about Elastic Search, but you don't have any search background, you could still start the system design with server, databases and other basic concepts, to solve the problem. It doesn't make sense for a candidate without search background to know details about Elastic Search, but it does make sense for a candidate to solve the problem with its knowledge.

I am also a very junior engineer, but I am willing to spend some time working on this. The approach I am using, is to use less certain knowledge, but more generic knowledge. It is more like my thought process how I iterate the solution step by step. So that:
1. It is more beginner friendly
2. It follows the thought process
3. Most importantly, it is a practice for myself
